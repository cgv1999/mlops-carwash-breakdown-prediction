# ML-манифест: Предиктивное обслуживание автомоек "NDA"

## 1. Предыстория

**Заказчик:** Федеральная сеть автомоек "NDA".

**Текущая ситуация:**
- 50 адресов по городу, на каждом 2-4 моечных бокса (всего 150 боксов).
- Поломки оборудования происходят внезапно - бокс встал, вызвали сервисного инженера.
- Механики не знают заранее, какой бокс может выйти из строя - обслуживание полностью реактивное.
- Время простоя одного бокса: от 4 часов до 2 дней.
- Суммарно по сети: 8-12% рабочего времени боксы простаивают.

**Проблема:** Отсутствие системы предсказания поломок. Механики не знают, какой бокс может сломаться в ближайшее время, поэтому обслуживание реактивное - выезжают только по факту поломки.

---

## 2. Ценностное предложение

**Что дает продукт:**
- Прогноз: какой бокс и на каком адресе сломается в ближайшие 7 дней.
- Снижение времени простоя боксов с 10% до 5% (в 2 раза).
- Сохранение выручки: 250 000 рублей в месяц.

**Какие трудности облегчает:**
- Механики заранее знают, на какой адрес ехать = профилактика.
- Снижается нагрузка на диспетчерскую службу.
- Уменьшается время реакции на инцидент.

---

## 3. Цели

1. **Бизнес-цель:** Снизить долю времени простоя боксов с 10% до 5% (сохранить 250 000 рублей/мес).
2. **ML-цель:** Для каждого бокса предсказывать вероятность поломки в ближайшие 7 дней (бинарная классификация: 1 - сломается, 0 - нет).
   - Recall (полнота) > 80% - чтобы не пропустить реальную поломку.
   - Precision (точность) > 60% - чтобы механики не выезжали зря.
3. **Операционная цель:** Интеграция прогнозов через API в систему управления ремонтами.

---

## 4. Решение

**Фичи (признаки):**

**Статические (характеристики бокса):**
- Год запуска бокса (возраст оборудования)
- Тип расположения: сквозной / тупиковый
- Близость к центру города (км)
- Количество боксов на адресе (2, 3 или 4)
- Производитель оборудования (категориальный: Karcher, Istobal, CWK)

**Динамические (меняются со временем):**
- Среднее количество моек в день за последние 30/60/90 дней
- Средний чек на адресе (руб)
- Количество отзывов на адрес (общее и за последний месяц)
- Средняя оценка (рейтинг) адреса
- Количество поломок этого бокса за последние 3/6/12 месяцев
- Среднее время простоя при прошлых поломках (часов)
- Дней с последней поломки
- Дней с последнего техобслуживания

**Сезонные:**
- Месяц (сезонность: зимой больше грязи = выше нагрузка)
- День недели (выходные vs будни)

**Интеграции:**
- PostgreSQL (данные о боксах, адресах, поломках).
- Airflow (оркестрация ежемесячного переобучения).
- MLflow (трекинг экспериментов, реестр моделей).
- FastAPI (сервинг прогнозов).
- Feature Store (агрегированные признаки).

**Ограничения:**
- Прогноз только на 7 дней вперед.
- Только для боксов с историей > 3 месяцев.
- Не предсказываем тип поломки, только факт.

**Не входит в продукт:**
- Система управления ремонтами (только API для нее).
- Автоматический заказ запчастей.
- Маршрутизация механиков.

**Заявляемый уровень зрелости ML-системы: 2**

## 5. Осуществимость

**Ресурсы:**
- Разработчик: 1 человек.
- Данные: исторические данные сети автомоек за 3 года (боксы, адреса, поломки).
- Инфраструктура: Docker Compose (локальная разработка), облачный сервер (демонстрация).

**Срок:**
2 недели.
- Неделя 1: генерация данных, baseline, фича-стор.
- Неделя 2: Airflow DAG, API, MLflow, мониторинг, документы.

**Риски:**
- Первый риск - внешние факторы, не попавшие в признаки. Скачки напряжения, качество воды, новый поставщик автохимии могут вызывать поломки, но не фиксируются в данных заказчика. Модель может ошибаться в таких случаях. Это задокументированное ограничение первой версии системы.

- Второй риск - изменение паттернов нагрузки. Открытие новой автомойки по соседству или перекрытие дороги меняет поток клиентов. Модель, обученная на старых данных, начнет ошибаться чаще. Для этого в системе предусмотрен мониторинг дрифта признаков и возможность внепланового переобучения, если Recall упадет ниже порога до конца месяца.

- Третий риск - сезонность, которую не ловят месячные лаги. Аномально грязный сезон (теплая зима без снега, затяжные дожди) может резко изменить нагрузку. Месячное переобучение может не успеть за такими изменениями. Закладываем в архитектуру возможность сокращения интервала переобучения до недельного без изменения кода пайплайна.

## 6. Данные

**Источники данных:**

`boxes.csv` - справочник боксов:
- box_id (идентификатор бокса)
- address_id (привязка к адресу)
- год_запуска
- тип_расположения (сквозной / тупиковый)
- близость_к_центру (км)
- производитель_оборудования (Karcher, Istobal, CWK)
- количество_боксов_на_адресе (2, 3 или 4)

`addresses.csv` - справочник адресов:
- address_id
- район
- количество_отзывов_всего
- количество_отзывов_за_месяц
- средняя_оценка (рейтинг)
- средний_чек (руб)

`breakdowns.csv` - история поломок:
- box_id
- дата_поломки
- время_простоя_часов
- дата_последнего_ТО (техобслуживания)

**Feature Store (агрегированные признаки):**
- Среднее количество моек в день за 30/60/90 дней
- Количество поломок за последние 3/6/12 месяцев
- Среднее время простоя при прошлых поломках
- Дней с последней поломки
- Дней с последнего техобслуживания
- Месяц, день недели (сезонные признаки)

**Разметка:**

Целевая переменная - `will_break_7d`. Это бинарный признак: сломается бокс в ближайшие 7 дней или нет.

Как размечаем:
- Берем конкретную дату, например 1 марта.
- Смотрим в историю поломок: у бокса №5 есть поломка 5 марта.
- 5 марта - это в пределах 7 дней от 1 марта (1 марта + 7 дней = 8 марта).
- Значит, для бокса №5 на дату 1 марта ставим `will_break_7d = 1` (да, сломается).
- Если поломок в ближайшие 7 дней нет - ставим `0`.

Так проходим по всем датам и всем боксам. Каждая строка в обучающей выборке - это "бокс №X на дату Y", и мы знаем, сломался ли он в ближайшую неделю.

## 7. Метрики (в порядке приоритета)

**Приоритет 1 - Время простоя боксов (% от рабочего времени).**
Это главная бизнес-метрика заказчика. Целевое значение: менее 5%. Именно ради снижения простоя с текущих 10% до 5% и строится система. Все остальные метрики - инструментальные, они нужны, чтобы этой цели достичь.

**Приоритет 2 - Recall (полнота).**
Доля реальных поломок, которые мы предсказали. Целевое значение: выше 80%. Пропустить поломку (false negative) гораздо дороже, чем отправить механика на ложный выезд. Непредсказанная поломка - это несколько часов простоя и потерянная выручка. Поэтому Recall для нас важнее точности.

**Приоритет 3 - Precision (точность).**
Доля предсказанных поломок, которые действительно случились. Целевое значение: выше 60%. Если точность слишком низкая, механики начнут игнорировать предупреждения. Порог 60% означает, что из 10 выездов минимум 6 - по делу, и это приемлемо для бизнеса.

**Приоритет 4 - F2-score.**
Компромиссная метрика, которая объединяет Recall и Precision, но с удвоенным весом Recall. Целевое значение: выше 0.7. Позволяет сравнивать модели между собой, не сводя все к одной цифре, но помня о приоритете полноты.

**Почему не Accuracy (доля правильных ответов):**
Поломки - редкое событие. Допустим, из 1000 боксо-дней поломка случается в 50 случаях (5%). Если модель всегда говорит "не сломается", она права в 950 случаях из 1000 - accuracy 95%. Отличная цифра, но реальных поломок не предсказано ни одной. Accuracy бесполезна для несбалансированных классов, поэтому мы ее не используем.

## 8. Оценка качества модели

**Офлайн-метрики (на отложенной выборке 20%):**
- Confusion Matrix - видим, сколько поломок предсказано, сколько пропущено.
- Recall, Precision, F2-score - основные метрики для принятия решений.
- PR-AUC (площадь под Precision-Recall кривой) - для сравнения версий модели. В отличие от ROC-AUC, эта метрика не завышает качество при несбалансированных классах.

**Онлайн-метрики (ежемесячный мониторинг):**
- Количество пропущенных поломок (false negative) за месяц - главный тревожный показатель.
- Дрифт признаков (Evidently AI) - проверяем, не изменилось ли распределение входящих данных по сравнению с обучающей выборкой.
- Время простоя боксов в часах (из ERP заказчика) - бизнес-метрика, ради которой все затевалось.

**Порог для вывода модели из эксплуатации:**
Модель считается устаревшей и подлежит замене, если за отчетный месяц случилось хотя бы одно из следующих событий:
- Recall опустился ниже 60%.
- Количество пропущенных поломок превысило 5 случаев.

**Механизм замены модели:**
1. Airflow DAG обучает новую модель и регистрирует ее в MLflow Model Registry со стадией Staging (аналог тестового контура).
2. Новая модель (Staging) сравнивается с текущей боевой моделью (Production) по Recall и Precision.
3. Правило замены: новая модель должна иметь Recall выше старой, при этом Precision не ниже 60%. Если Precision упал ниже порога - модель остается в Staging, требуется ручная проверка.
4. Если условия выполнены - новая модель переходит в Production, старая - в Archived.
5. FastAPI всегда загружает из MLflow ту модель, которая находится на стадии Production.

## 9. Подбор модели

Итеративный подход. Начинаем с простого, последовательно усложняем.

**Итерация 1 - Logistic Regression.**
Самая простая модель. Быстро обучается, легко интерпретировать: видим, какой признак и насколько влияет на вероятность поломки. Берем как baseline - все, что мы построим дальше, должно быть лучше нее.

**Итерация 2 - Random Forest.**
Деревья решений ловят нелинейные зависимости и взаимодействия признаков, которые логистическая регрессия не видит. Например, сочетание "старый бокс + высокая нагрузка" может давать риск поломки, неочевидный по отдельности. Смотрим, дал ли прирост по Recall.

**Итерация 3 - XGBoost.**
Градиентный бустинг - более мощный алгоритм, чем Random Forest. Настраиваем гиперпараметры (глубина деревьев, скорость обучения) через кросс-валидацию. Подбираем порог классификации так, чтобы максимизировать Recall при Precision не ниже 60%.

**Итерация 4 - CatBoost.**
Бустинг с нативной поддержкой категориальных признаков (производитель оборудования, тип расположения, район). Не требует ручного кодирования категорий, меньше шансов допустить ошибку в препроцессинге. Сравниваем с XGBoost по F2-score на отложенной выборке, лучшую берем в прод.

## 10. Инференс

**Режим:** Батчевый.

**Расписание:**
- Ежемесячно (1 числа в 02:00) Airflow DAG переобучает модель на всех накопленных данных и регистрирует новую версию в MLflow Registry. Если качество выше текущей Production-модели - заменяет ее.
- Ежедневно (в 03:00) Airflow DAG загружает актуальную модель из MLflow, собирает свежие признаки из Feature Store и генерирует прогноз на 7 дней вперед для всех боксов. Результаты сохраняются в PostgreSQL.

**Сервинг:**
- FastAPI endpoint `GET /predict/box/{box_id}` - возвращает вероятность поломки в ближайшие 7 дней. Данные берутся из PostgreSQL (результат последнего ежедневного прогноза).
- Endpoint `GET /predict/address/{address_id}` - возвращает список боксов на адресе с вероятностями поломок. Удобно для диспетчерской: открыл адрес и видишь, какие боксы в зоне риска.

## 11. Обратная связь

**Источники обратной связи:**

Данные о фактических поломках из ERP заказчика - основной источник. Через 7 дней после каждого прогноза мы можем сравнить, что предсказали и что случилось на самом деле. На этом строится расчет Recall и Precision онлайн.

Время простоя боксов - бизнес-метрика, по которой заказчик оценивает эффективность системы. Если простой не снижается, модель не помогает, даже если ML-метрики выглядят хорошо. Это главный сигнал для смены подхода.

Количество ложных выездов - косвенный показатель Precision. Если механики жалуются на частые ложные тревоги, система теряет доверие, даже при хорошем Recall. Учитывается при принятии решения о выводе модели в прод.

**Цикл обратной связи:**
1. Ежемесячно Airflow собирает данные о фактических поломках за прошедший месяц.
2. Сравнивает прогнозы с фактом, считает Recall и Precision онлайн.
3. Если Recall < 60% - запускает внеплановое переобучение.
4. Результаты сравнения логируются в MLflow для истории.

**MDD для принятия решений: Да.**
При сравнении двух версий системы (текущая модель vs новая модель) используем статистический тест для сравнения времени простоя боксов. Нулевая гипотеза: время простоя одинаковое. Уровень значимости: p-value < 0.05. Решение о замене модели оформляется как ADR (Architecture Decision Record).
